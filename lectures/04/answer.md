- **気づき・疑問**：

  モデルを変更するだけで、人間の判定との一致率が改善する項目があることが分かった。一方で、モデルを変更しても解決しない問題があり、採点基準そのものの設計が重要だと感じた。

  特に、要確認となった問題は、モデルの能力だけではなく、何を合格とするかが決まっていないことに原因があった。

  また、一部の評価項目が改善しても総合一致率は変わらず、どの指標で評価するかによって改善の捉え方が異なることも分かった。

  今回は10件という少数の評価であり、モデルの優劣を断定することは難しい。今後は人間の評価の一致度や評価基準の妥当性も含めて検証することが重要だと感じた。


## 宿題

- **取り組んだレベル**：発展

- **やったこと**：

  フロンティアモデルの評価に用いられるベンチマークとして、**τ²-bench（Tau-Squared Bench）**を選び、論文を調査した。

  - 論文：Barres V, et al. *τ²-Bench: Evaluating Conversational Agents in a Dual-Control Environment*. ICML 2026.
  - URL：https://proceedings.mlr.press/v306/barres26a.html
  - 対象：AIエージェントと利用者が対話しながら、互いに操作可能な環境で課題を解決する能力の評価

  論文に掲載された通信障害の具体的な課題定義1件と、航空券予約・商品キャンセル・モバイル通信障害の利用者指示例3件を読み、内容と難しさを整理した。

  また、論文の「3.2. Domain and task creation」「3.3. Task evaluation」「4.3. How does dual-control impact benchmark reliability?」から、評価課題の作成方法、検証手順、採点方法を調べた。

- **結果**：

  **1．調査した評価課題・シナリオ例**

  | 課題例 | 内容 | AIにとって難しい点 |
  |---|---|---|
  | 通信サービスの復旧 | 機内モードとSIMカードの不具合を解決する | 複数の原因を特定し、利用者に適切な操作を促す |
  | 航空券予約 | 希望する便、座席、人数、予算、支払い方法を守って予約する | 複数の条件と条件分岐を正確に扱う |
  | 商品キャンセル | 配送状況に応じて、部分キャンセル・全体キャンセル・キャンセル中止を判断する | 利用者の条件付きの希望を守る |
  | モバイル通信の改善 | 通信速度を改善する。ただし契約プランは変更しない | 利用者の条件を守りながら、問題の解決を確認する |

  ※最初の1件は初期状態と評価条件を含む完全な課題例である。他の3件は利用者シミュレーターに与える指示の例であり、完全な課題定義ではない。

  **2．評価課題の作成者と作成方法**

  論文の著者は5名である。ただし、個々の課題の作成に実際に何人が関与したかは、確認した記載からは特定できなかった。

  新たに構築した通信サポート領域では、次の手順で評価環境と課題を作成していた。

  1. LLMを利用してAIエージェント側のデータベースと操作ツールを作成する。
  2. LLMを利用して利用者側の模擬スマートフォンと操作ツールを作成する。
  3. 初期状態・解決操作・検証条件を持つ基本課題を組み合わせ、評価問題を自動生成する。
  4. LLMを利用してAIエージェントが守る業務ルールを作成する。
  5. 人間がプログラム、業務ルール、基本課題を修正する。

  通信サポート領域では、15の基本課題グループを組み合わせて2,285件の課題を生成し、その中から障害の種類や複雑さの分布を考慮して114件を抽出していた。

  **3．評価課題の検証方法**

  LLMが生成したプログラムは、人間が修正を加え、単体テストに合格するまで確認していた。

  また、課題については、設定した初期状態に解決操作を適用すると成功条件が満たされること、必要な操作が完了する前には成功条件が満たされないことを自動的に検証していた。

  利用者シミュレーターの品質評価では、各対話を2名の評価者が独立して確認した。通信サポート領域の50対話では、重大なエラーが3件（6%）、その他のエラーが5件（10%）、合計8件（16%）報告されていた。

  なお、2,285件から114件への減少は評価用データの抽出によるものであり、残りが不適切な問題として除外されたことを意味しない。

  **4．AIの採点方法**

  τ²-benchには、データベースの状態確認、最終状態の検証、対話内容の検証、必要な情報の伝達確認、操作履歴の照合などの評価方法が用意されている。

  新たに作成された通信サポート領域では、最終的な環境状態を検証する関数によって課題の成功を判定していた。

  例えば、AIが「通信が回復しました」と回答するだけでは成功にならず、実際に模擬スマートフォンが接続可能な状態になったことを確認する。

  **5．今回の授業の評価セットとの比較**

  | 比較項目 | 第4回の演習 | τ²-bench |
  |---|---|---|
  | 評価対象 | 学習支援AIの回答 | 対話・操作による課題解決 |
  | 問題数 | 10件 | 通信領域で114件（生成数2,285件） |
  | 問題作成 | 講師が用意 | LLMとプログラムによる生成、人間による修正 |
  | 検証 | 人間のラベルとの比較 | 単体テスト、自動検証、人間による対話評価 |
  | 採点 | 人間・LLMによる基準別評価、コード判定 | 通信領域では最終環境状態の検証 |
  | 評価の中心 | 回答が基準を満たすか | 課題を実際に解決できたか |

- **気づき・疑問**：

  今回の演習ではAIの回答を読んで採点したが、τ²-benchでは、正しい説明ができるだけでなく、実際に課題を解決できたかを評価していた点が印象的だった。

  また、評価問題を作る段階で、初期状態、解決に必要な操作、成功条件をあらかじめ定義することで、採点の曖昧さを減らせることが分かった。

  一方、客観的な成功条件を設定できても、利用者との対話が自然であったか、相手の理解度に適した説明だったかまでは十分に評価できない可能性がある。

  看護師の問診練習用患者AIを作成する場合にも、患者の情報を正確に再現できたかという客観的な評価と、患者らしい自然な応答ができたかという専門家による評価を組み合わせる必要があると考えた。
